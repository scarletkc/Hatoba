## SSH to older network switches, and piped input for hatoba exec

Servers that offer only the NIST-curve key exchanges (`ecdh-sha2-nistp256`, `-nistp384`, and `-nistp521`) and SHA-1 Diffie-Hellman, as many older network switches do, now connect instead of failing with "No common Kex algorithm". Hatoba prefers those key exchanges after curve25519 and before Diffie-Hellman, as OpenSSH does.

`hatoba exec` passes its input to the command when it comes from a pipe or a file, as `ssh` does, so a script or a config file goes in without quoting: `hatoba exec db 'sh -s' < deploy.sh`, or `hatoba exec --sudo db 'tee /etc/app.conf >/dev/null' < app.conf`. From a terminal, the command's input stays empty. `hatoba cp` keeps the permissions of a file it replaces on the host, as `cp` and `scp` do, where a `600` file used to come back with the default permissions, and `--mode` sets them, such as `--mode 600`. A misspelled command such as `hatoba exce` fails and names the command it may mean, instead of opening Hatoba. The empty line that sudo-rs, Ubuntu's sudo since 25.10, prints after it reads the password no longer reaches the command's stderr.

On Windows 11, the translucent tab bar and navigation rail follow Hatoba's light or dark appearance instead of Windows', so they no longer turn grey when the two differ.

The `hatoba-cli` skill is shorter now that `hatoba --help` covers the rest: run the command under **Skill for coding agents** in **Settings → General** again to update it.

Installed versions update to this version from **Settings → About**. The sync Worker hasn't changed, so there is nothing to redeploy.
