## Copy from programs on a server, and a plugin for coding agents

Programs on a server, such as Codex, tmux and Neovim, can now copy text to this computer's clipboard. They ask the terminal to copy with OSC 52, which Hatoba used to ignore, so what you copied in them never reached the clipboard. One copy holds up to about 750 KB of text, and longer text isn't copied. A program that asks to read the clipboard gets no answer, so no program learns what you copied elsewhere. While a program tracks the mouse, a drag goes to the program; on macOS, hold ⌥ while you drag to select text in the terminal instead, as Shift does on Windows and Linux.

Claude Code, Codex and DeepSeek Harness can now install the hatoba-cli skill as a plugin, `hatoba-agent-plugin`, which each stable release publishes to npm with the skill of that release, so the agent's copy of the skill follows Hatoba's. The [plugin's README](https://github.com/scarletkc/Hatoba/tree/main/packaging/agent-plugin) has the commands that install it in each agent. As with the skill, the agent works through the `hatoba` command, so **Use the hatoba command in terminals** and **Let other programs use saved hosts** in **Settings → General** have to be on.

`hatoba memory` now works only with the memories of a host: listing, `save` and `delete` all need `--host`. The global memories hold your preferences for Hatoba's assistant, so the command no longer lists or changes them, and a coding agent can no longer put its notes into every conversation in the app. With `--json`, each memory no longer has the `scope` and `host` fields.

On macOS, `hatoba exec` with a short input from a pipe or a file, such as `hatoba exec db 'sh -s' < deploy.sh`, often ran the command with no input about 10 seconds late, and still exited with 0. The input now arrives every time. On every system, when the input doesn't reach Hatoba within 10 seconds, Hatoba stops the command and `hatoba exec` exits with 255, instead of letting the command run with no input.

This version updates russh, the library behind Hatoba's SSH connections, to a version with its latest security fixes. With it, servers with an ECDSA P-521 host key that pad its signatures, such as Huawei S6720 switches, no longer fail during key exchange.

Sync Worker 0.1.3 updates Hono, the framework the Worker runs on, to a version with its latest security fixes, and changes nothing else. After Hatoba updates, the sync status page shows that a Worker update is available. Choose **Update Worker** and give it a Cloudflare API token with the same permissions as for the first deployment. Sync keeps working until you do.

Installed versions update to this version from **Settings → About**.
